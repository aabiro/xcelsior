## What the real run found that the rehearsal couldn't

1. **Rollback could have killed a Docker container's database.** Rollback ended with `pkill -x mariadbd` for stray daemons. That matches across PID namespaces, and on the tower it matched mempool's `mariadbd` inside Docker. Found in the first tower dry run, before any rollback ran there. Rollback now kills only host-namespace, non-container processes.
2. **A reinstall left MariaDB without system tables.** MariaDB's AppArmor profile (setuid/setgid commented out) denies the uid change `mariadb-install-db` makes during the package's postinst. Purging the package leaves the profile loaded, so the first install worked and the reinstall didn't. The tables are now created as the `mysql` user when missing, and rollback unloads the stale profile.
3. **Rollback resurrected `/etc/default/slurmd`** on the ASUS (above). Fixed.
4. **The sleep-target preflight check failed falsely** with all four targets masked (`systemctl show` prints blank lines between units). Fixed.

## Observations

- **The tower's GPU is shared.** The health check logged five non-Slurm processes on the RTX 3060: MPS, pxl-publisher, pe-test-gpu-worker and two in a Docker container. It logs them and doesn't drain. GPU-1 and POD-1 measured a shared GPU.

## Rebuild on SchedMD's Slurm 25.11.8 (run `r1108034352`)

Later the same day the cluster was rebuilt on SchedMD's own packages, closing the CVE item above. Evidence: [evidence/r1108034352/](evidence/r1108034352/).

- **Packages.** `05-build-slurm-debs.sh` built slurm-smd 25.11.8-1 from SchedMD's tarball. The tarball unpacked to a tree identical to GitHub's `slurm-25-11-8-1` tag, and its sha256 is pinned in the script. The build ran in a throwaway container, so neither machine got build tools. The NVML, MySQL, munge, cgroup/v2 and preempt/qos plugins are all in `slurm-smd`, and the packages declare no NVIDIA library dependency, so neither machine's driver is touched.
- **Rehearsal.** V-1 to V-13 and 26 of 26 suite cases passed.
- **Rollback of the Phase 0 install.** R-2 to R-4 pass on both machines with nothing left behind: 7 packages on the ASUS and 23 on the tower, each exactly the recorded set, none added. `/etc/default/slurmd` didn't come back, sshd dropped the service account's block, and the stale `mariadbd` AppArmor profile was unloaded after the purge. The kernel logged the `profile_remove`, confirming the purge alone leaves the profile loaded. mempool's containers kept restart count 0.
- **Install.** It worked on the first attempt on both machines, with no MariaDB fallback needed. Both nodes run `slurm 25.11.8`, from slurm-smd, slurm-smd-client, -slurmctld, -slurmd and -slurmdbd 25.11.8-1.
- **Checks.** V-1 to V-13 all pass: V-6 (NVML detects `rtx_3060`), V-12 (Docker and runners unchanged) and V-13 (`slurm 25.11.8`). The suite passes 26 of 26, SEC-1, SEC-2 and SYNC-1 included, and V-12 and V-13 pass again afterwards.

The adapter needed no change for 25.11.8. The error codes, `scancel -v` handling, `CANCELLED by <uid>` parsing and the sacct fallback all behaved as on 25.11.2.

Later still, the reconciler's first slice (Phase 1) ran against the same cluster. SYNC-1 passed with the new rule that a mapping settles only after its job leaves the controller (run `r1108041255`). SYNC-2 passed (run `r1108041716`): five open jobs cost exactly one `squeue` and one `sacct`, the running job stayed open, and the four finished ones settled. The first SYNC-2 attempt also flagged SYNC-1's two jobs as orphans: adapter-named, with their mappings deleted by SYNC-1's cleanup.

The scenario matrix then ran against the reconciler (run `r1108113648`, [evidence/r1108113648/](evidence/r1108113648/)). All six cases passed:

- **SCEN-1, requeue:** open through the requeue; settled completed; accounting runs `REQUEUED`, `COMPLETED`.
- **SCEN-2, spot preemption:** a spot-QoS GPU job preempted by a normal one stayed open through the preemption and settled completed; runs `PREEMPTED`, `COMPLETED`.
- **SCEN-3, out of memory:** settled `failed` / `OUT_OF_MEMORY`.
- **SCEN-4, SPECIAL_EXIT hold:** `held`, not failed, and still open; released, it ran again.
- **SCEN-5, suspend/resume:** `suspended`, not pending; resumed, it was running again.
- **SCEN-6, node failure:** slurmd killed on the asus. While the node was down the job was pending and the mapping open, and accounting recorded `NODE_FAIL`. The node rejoined on its own once slurmd restarted.

After the reconciler learned to tell jobs under one id apart by name (job-id reuse, migration 153) and gained the output cache (migration 154), the whole suite ran again with the scenarios (run `r1108142218`, [evidence/r1108142218/](evidence/r1108142218/)): 33 of 33 passed, SYNC-1, SYNC-2 and SCEN-1 to SCEN-6 included, with the same outcomes as above. The reconciler now accepts a job under a mapping's id only if its name is that mapping's `xcl-<xcelsior job id>`, so the suite registers each job under the id it submitted it with, as production does. The orphans it reported are jobs that had no mapping: earlier cases submit without registering (LIFE-4, FAIL-6 and SEC-1's jobs among them), and SYNC-2's cleanup deletes its own mappings. Job-id reuse itself is staged with a scripted cluster (`tests/test_slurm_reconciler.py::TestJobIdReuse`), not here: renumbering needs a controller state wipe.

Then the rest of Phase 1 (items 1.2 and 1.7, migration 155) ran against the cluster, after the gate was updated on the tower with only its new `gate` step (it now admits `scontrol show config` and the `.progress` file): run `r1108170818`, [evidence/r1108170818/](evidence/r1108170818/), 36 of 36 passed, with SCEN-1 to SCEN-6 again unchanged. The three new cases:

- **REG-1, the registry transport:** the tower registered with the host key this account already trusts and the adapter's key. The connection check captured all 19 config facts (Slurm 25.11.8, MinJobAge 60 s, MaxJobId 67043328, PreemptMode REQUEUE, AccountingStoreFlags `job_comment,job_script` among them). After the first pass the ControlMaster was up, and the second use found it up before sending anything. A cluster registered with a wrong pin was refused with `host_key_mismatch`.
- **PROG-1, a job's own progress:** the job wrote its progress file as the contract says (temporary file, then rename), one pass fetched it through the gate, and the read showed fraction 0.5 and "half way", reported by the job and not stale.
- **VERDICT-1, the success verdict:** two jobs exited `0:0`. The one whose `srun false` step failed first recorded DerivedExitCode `1:0`, so it reads `failed`; the other `succeeded`.

The cluster was left running, with services disabled at boot.
